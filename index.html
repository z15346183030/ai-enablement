01

一个人，八个角色

公司里做 AI 赋能，最难的不是技术，是这八件事你得同时兜得住。
01

找到值得做的场景

大部分公司不缺 AI 想法，缺的是判断哪个值得先做。

  • 把业务流程拆成节点，标出谁在等谁、哪里最耗时
  • 按「价值 × 可行性 × 阻力」三轴排序，选出第一个样板
  • 把「太慢了」翻译成可验收的指标：周期、工时、错误率
  • 明确哪些是 AI 能解决的，哪些是组织和权限问题
02

一周做出能用的原型

不写 PPT 画饼，先给你一个能点开的东西。

  • Python + FastAPI 全栈，前端到后端一个人写
  • 先做最窄的一条链路，能跑通再谈扩展
  • 用真实数据跑，不用玩具样本糊弄
  • 原型阶段就把成本和延迟算进去，避免后期推翻
03

把数据接进来

模型再强，喂进去的数据口径不一致，输出就是精致的错误。

  • 源系统盘点：ERP / CRM / WMS / 一堆 Excel，逐个确认取数方式
  • 口径对齐：同一个「订单金额」三张表三个数，先定文档再写代码
  • 清洗、去重、增量同步、幂等写入
  • 向量化与索引，让检索层能稳定召回
04

让模型真的答得准

RAG 不是「把文档塞进去」就完事，召回质量决定一切。

  • 切分策略对比、混合召回（向量 + 关键词）、重排
  • 答案必须能点回原文，不给用户「听起来对」的东西
  • Agent 编排：路径固定的用状态机，路径开放才交给模型
  • 工具权限在代码层强制，不靠 prompt 里写「请不要」
05

让它不出错

这是我花时间最多的一块，也是 demo 和产品真正的分界线。

  • 建立评测样本库，每次改动跑全量回归
  • LLM-as-Judge 多评委 + ICC 一致性检验，避免单评委漂移
  • 双闸门：准确率下限 + 样本量下限，不达标就阻断发布
  • 线上失败案例自动回流成新样本，越用越准
06

让它跑得住、算得过账

上线不是终点，是成本开始计费的地方。

  • Docker 容器化、Linux 部署、CI/CD、版本可回滚
  • 全链路 trace：检索、重排、生成、工具调用逐段看耗时
  • 模型分级路由：简单请求走小模型，复杂请求才升级
  • PII 护栏放在入口，敏感数据不出域
07

让同事都会用

一个人做得再好也只有一双手，赋能的意思是让能力长在别人身上。

  • 把高频任务做成模板和内部工具，降低使用门槛
  • 写清楚什么该用 AI、什么不该用，避免全员乱试
  • 小范围培训 + 陪跑，先让两三个人用出效果
  • 沉淀内部知识库，让好用的 prompt 和流程可复用
08

让这件事持续下去

AI 半年一变，今天选的技术栈明年可能就废了。

  • 工具选型：按团队实际能力选，不追最热的
  • 建立评估机制，新模型出来能快速横向对比
  • 把每个项目的经验抽象成可复用组件
  • 跟踪成本曲线，让 AI 的投入产出始终算得清

Multi-Agent Code Studio

评测体系

问题AI 生成代码的质量方差极大，团队没法判断「这次能不能用」，只能靠人肉看。

这些不是练手项目。它们对应的是公司里没人负责、但必须有东西能用的那些环节：看懂别人的代码、把客户给的 Word 变成能进库的文档、上线前扫一遍密钥、改配置不留噪音。
我自己的标准很硬：一个文件、只用标准库、复制过去就能跑——因为「装不了包」的那台机器，才是真实环境。而且每个都带测试：1.35 万行工具代码配 0.81 万行测试。

05

不会的，我学得很快

AI 这个领域没有人的知识是完整的。真正的差别是补的速度。

上面那张技术栈不是终点。这个行业每半年换一轮，今天会的东西明年一定不够用，所以我更在意的是自己补新东西的速度，而不是现在手里有什么。

我的方法很笨但有效：直接拆一个真东西下来。想学某个工具，就把它复刻一遍；想搞懂某个系统，就把它逆向拆开，每一步都写清楚为什么这么设计。拆完的东西都是能跑的程序，不是笔记。

没做过的领域，给我一到两周，我能做到能用；给我一个月，我能做到能教别人。

所以面试时如果你问到一个我没碰过的技术，我不会含糊过去。我会告诉你我没做过，然后告诉你我打算怎么在一周内把它跑起来 —— 并且给得出具体的路径。
